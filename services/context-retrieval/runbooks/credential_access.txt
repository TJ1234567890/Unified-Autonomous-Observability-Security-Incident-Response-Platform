RUNBOOK: Credential Access / Secret File Read
Severity: High
Tags: credentials, passwd, shadow, sudoers, secrets, credential-dumping

TRIGGER CONDITIONS
- openat or read of /etc/passwd, /etc/shadow, /etc/sudoers
- Access to /root/.ssh/id_rsa or /home/*/.ssh/id_rsa
- Process reading files matching *password*, *secret*, *credential*, *.pem, *.key
- Memory access patterns consistent with credential dumping (mmap of authentication process memory)

IMMEDIATE ACTIONS (first 5 minutes)
1. Identify what was accessed and by whom:
   - Query: log_type=deep_kernel, feat_args_has_sensitive_path=1
   - Note the process_name, user_id, and exact file accessed
   - Was /etc/shadow accessed? If yes, treat all local user passwords as compromised

2. Check if the data was exfiltrated:
   - Did the same process or a child process make a network connection after the file read?
   - Query for outbound connections from the same process_id in the 5 minutes following the event

3. Lock accounts that may have been exposed:
   - If /etc/shadow was read: force password reset for all local accounts on the host
   - If SSH keys were accessed: revoke the affected keys immediately in authorized_keys

INVESTIGATION
- What process accessed the sensitive file?
  - Legitimate: passwd, shadow-utils, sshd during normal auth operations
  - Suspicious: python, bash, wget, unknown binaries
- Who launched that process? Trace the parent_process_id chain
- Was this a one-time access or repeated reads? Check event frequency over the past hour
- Were the accessed credentials used for lateral movement? Check auth logs on other hosts

CREDENTIAL ROTATION CHECKLIST
- /etc/shadow accessed: rotate all local user passwords
- SSH private key accessed: revoke key, issue new key pair, update authorized_keys on all hosts
- Application config file accessed: rotate API keys, database passwords, service tokens
- AWS credentials file (~/.aws/credentials): rotate IAM keys immediately via AWS console
- Kubernetes service account token: revoke and reissue via kubectl

ESCALATION
- If /etc/shadow was accessed by a non-root, non-system process: escalate immediately
- If subsequent network exfiltration is detected: escalate to Critical

RECOVERY
- After rotating credentials, audit all systems that accepted the potentially compromised credentials
- Enable file integrity monitoring (FIM) on sensitive paths
- Review and tighten file permissions: /etc/shadow should be mode 640, owned by root:shadow
